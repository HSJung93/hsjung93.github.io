## 왜 필요했나: 노트북 안 SQL, 원시 .sql + 셸, 파이썬 러너. 실행 방식 4종, 테스트 0, 리니지 0, 운영 환경 하나뿐이라 검증을 운영에서



## 왜 지금이었나: 사업부서 월간 통계 과제(11주)가 첫 적용 기회가 된 경위. 외주·노코드 대신 직접 만들기로 한 판단



## 도구 선택의 시행착오: 업계 표준(dbt + Airflow + Cosmos)이 워커가 SageMaker Processing Job 인 인프라에 안 맞음 → dbt-athena + 매니지드 Airflow + lineage 시각화까지만. 포기한 것과 그 이유



## 첫 적용: 월간 통계 마트. "축은 파이프라인이, 조합은 화면이" 설계, 더할 수 없는 DISTINCT, 골든 테스트(마감월 seed), dbt 실행 현황 페이지(manifest/run_results). 자산화 DB 제약(테이블 생성 불가) → incremental + pre_hook DELETE



## 시행착오 1: 원천 데이터의 함정. 지연 확정 누락, 재라벨, 일별 원천 60일 보존. 병렬 마트 비교로 재현하고 적재 기준월을 바꾼 과정



## 시행착오 2: 합의. 저장소 진단 문서를 "확정 규칙 아님"으로 낸 이유, 담당자 회신 지연과 "확인 필요" 표



## 시행착오 3: 전환 방식. 3개월 갈라진 브랜치를 머지하지 않고 옮겨 적기, 치환 → 역치환 대조, sandbox + 양방향 EXCEPT 병행 검증, 백필 방침 비교(4항목), 하루 컷오버



## 시행착오 4: 규칙은 약속, 강제는 설정. 운영 브랜치 직접 push 절반 → 보호 브랜치. CLAUDE.md 가 .gitignore 에 막혀 새 clone 에서 규칙 0줄이던 일. MR 4단 본문·정적 확인



## 지금 상태와 숫자: 전환 계획 27건, dev 환경 계획 20건, 노트북 4개 → 모델 9개, MR 리뷰 39건. 아직 안 된 것



## 다시 한다면: 전환은 기술보다 "누가 어디에 언제 쓸지"의 합의 문제. 사람이 안 봐도 같다고 증명되는 장치가 리뷰 부담을 줄인다
